# 丢包率：口径、采集与展示

配套代码：
- 口径与窗口算术（纯函数）→ `desktop/telemetry/loss_window.py`
- 下游两级记账 → `desktop/streaming/h264_viewer.py`（`_note_hole` / `declare_loss`）
- 上游缺口记账 → `server/rtp_relay.py`（`_note_upstream_seq_locked`）
- 采集与上报 → `desktop/telemetry/latency_monitor.py`、`server/routers/video.py`
- 展示 → `desktop/modules/latency_panel.py`（丢包段）、`desktop/app.py`（底栏）
- 测试 → `test/test_loss_rate.py`

## 1. 为什么不能只有一个「丢包率」

链路有 **两级恢复**（`docs/video-latency-optimization.md` §4.3）。一个包丢了，
先由 NACK 重传补回，补不回才走 `declare_loss` 等 IDR 回退。这两级一旦合成一个
数字，就分不清两种完全不同的现场：

| 现场 | 线上丢包 | 最终丢失 | 结论 |
|---|---|---|---|
| 恢复层在满负荷工作 | 5% | 0% | 链路差，但**画面是好的** |
| 恢复层已经跟不上 | 5% | 2% | 链路差**且**画面在花屏 |
| 断流 / 重启 | — | — | 计数器复位，不是丢包 |

所以口径必须分层，而且**主数字用最终口径**：延迟有唯一量纲（ms，用户能直接判断
「能不能玩」），丢包率是排障量 —— 它只在「画面已经不对」时被人看。把 5% 显示成
主数字会让人去查一个根本不存在的问题。

## 2. 口径定义

### 下游（server → 桌面，viewer 数）

| 字段 | 含义 | 记账点 |
|---|---|---|
| `wire_lost` | **线上**：链路真实丢过的 RTP 序号数，**含**后来被 NACK 补回的 | 发现空洞时按增量记（`_note_hole`） |
| `final_lost` | **最终**：空洞过 `REORDER_S`(40 ms) 仍未补上、被判丢的 | `declare_loss` |
| `recovery_pct` | `(wire − final) / wire` | 推导；无线上丢包时为「—」 |

`wire >= final` 恒成立（有测试钉死）。差值就是重传白干的量 —— 「重传有没有在
真的干活」是唯一读数。

一个序号只记一次：同一空洞在 40 ms 窗口内被反复观测，且 `nmiss` 会随新包到达
变深，所以按「比上次记过的多出来的部分」累加。空洞结束时必须清基线，否则
u16 的 playhead 每 ~55 s 绕回一次时，下一个空洞会拿上一个的基线比而短记。

### 上游（K230 → server，relay 数）

| 字段 | 含义 |
|---|---|
| `up_lost` | 中继侧观测到的序号缺口（**只有线上口径**） |
| `up_gaps` | 发生缺口的次数 |
| `up_dup` | 同序号重传 + 半空间内的乱序 |
| `up_resets` | 上游重启（seq 回绕 / 归零）次数 |

**为什么上游没有最终口径**：中继不做重排。一个被 NACK 补回来的重传包在它看来
只是「乱序」，与真正的重复拷贝无法区分 —— server 没有信息量能判「最终损伤」。
最终损伤必须由下游的 `declare_loss` 判。面板上这一格带 `*` 标注就是为了不让
人误以为它和下游的「最终」可比。

**必须按入口端口分桶**：K230 同一 seq 同一包发往多个入口（8002/8003/8004），
共享一个 `max_seq` 会把「另一个端口的包」判成巨大缺口。

**为什么要有 `SEQ_RESET_MIN_DISTANCE`（8192）**：seq 是 16 位会回绕，从 45000
「前进」到 0 在模运算里就是一次合法的 `+20536`。不加这条判据，一次 K230 重启
会被记成 20536 个假丢失。阈值取半个序号空间的 1/4 —— K230 重传环只有 128 个
槽，任何真实链路都不可能连续丢 8192 个包。桌面端当初踩的就是这个坑
（`h264_viewer.py` 的 `SEQ_RESET_NOTE`），两侧常量同值由测试钉死，因为 server
不 import desktop。

## 3. 窗口 vs 累计

| 口径 | 用途 | 为什么不合适另一个 |
|---|---|---|
| **10 s 滑动窗口** | 面板主数字、告警色、曲线 | —— |
| 自流开始累计 | 日志、底栏、长时间统计 | 一次 WiFi 抖动把 `loss_pct` 永久拉高，之后再也回不来 |

改造前的 `h264_viewer.loss_pct` 就是只有累计口径的那个问题。现在两个都算：
窗口驱动显示，累计进日志（每 10 s 一条 `h264 rtp:` 统计行）。

窗口值的四个坑（都有对应用例，见 `test/test_loss_rate.py`）：

1. **计数器复位** → 差值为负，夹到 0。宁可少报也不报负丢包率。
2. **未上报样本**（`-1` 哨兵）→ 整条样本丢弃，绝不让 `-1` 参与减法。
3. **窗口不满** → 用最老的一条当基线，并把真实覆盖 `span_s` 返回；面板在
   页脚标注「窗口 6s」。不外推、不假装满窗。
4. **跨度为零** → 无数据（`-1`）而不是 0%。

分母统一是 `lost + rx`，其中 `rx` 是**入队**包数（已扣掉重复与过期包）——
用别的分母会在重传生效时把丢包率压低。

## 4. 展示方案

布局在延迟面板里，从属层级是刻意的：

```
LOSS · 丢包                          0.062%   ← 最终口径，12px 数字
[ 细条曲线 60s / 1s 一桶 / 0.5% 虚线 ]          ← 40px，只有最终口径
线上丢包 0.250%   最终丢失 0.062%
上游缺口* 0.000%  重传救回 75%
* 上游=中继侧观测的 K230→server 缺口，只有线上口径（中继不做重排）
```

设计取舍：

- **延迟是全场唯一的「大」元素**（26 px 主数字 + 110 px 曲线），丢包只配 12 px
  数字 + 40 px 细条。丢包必须常驻可见（它是排障入口），但不该跟延迟抢视觉权重。
- **曲线只画最终口径**。线上口径常常是锯齿状噪声，画出来会让人一直以为在坏。
  它以数字形式常驻，需要时看得到。
- **纵轴固定 0~3%**，超出发送到顶（与延迟条 800 ms 封顶同一套处理）。丢包率是
  长尾分布，固定上限让「0.03% vs 0.3%」这种真有意义的量级差看得出来。
- **无数据的桶画断开，不画 0**。把「没测到」画成 0% 是这类图最常见的撒谎方式。
- **零丢包的曲线用 OK 色而非 AMBER** —— 零丢包不该看起来像警告。
- **小数位分档**：< 1% 给 3 位、≥ 1% 给 2 位。一律 1 位会把 0.062% 显示成
  0.1%，而 0.1% 正是「有没有超告警线」的分界。
- **底栏区分「溢出丢」与「丢包率」**：前者是本机积压超预算主动丢的包，后者是
  链路没送到的包，成因完全不同，同一个「丢」字会让人查错方向。

### 阈值依据

`WARN_PCT = 0.5%` / `BAD_PCT = 2.0%`（窗口值）。30 fps / ~1200 pps 下 0.5% 约
等于每秒 6 个包 —— 低于 NACK 一轮 4 ms 的反应时间对应的可感知阈值，高于它说明
恢复层已经在满负荷工作。2% 以上画面上必然能看出损伤（宏块花屏 / 等 IDR）。
**这两个数是估算，不是实测**，实机跑 1080p/T3 后应重新标定。

## 5. 已知局限（诚实清单）

- 阈值未实机标定（见上）。
- 上游口径无法区分「重传补回」与「重复拷贝」，因此上游数字会**略高**于真实损伤。
- `up_lost` 只在中继**收到包**时才更新；K230 完全停流时它冻结在旧值，此时应看
  `live` / `staleness_ms` 而不是丢包率。
- 窗口是按累计计数器的差值算的，不做平滑；桶内突发丢包（如 IDR 帧丢 5 个包）会
  在曲线上是一个尖峰而不是被摊平 —— 这是有意的，尖峰才有定位价值。
- 曲线只覆盖探针的 `HISTORY = 120` 条样本（0.5 s 一条 = 60 s）。要更长的窗口
  曲线需要探针保留更多历史（内存换时间，当前 120 条 × 11 个字段很小）。

## 6. 加新口径时

1. 只在**一个**层记账（下游在 `h264_viewer`，上游在 `rtp_relay`），不要在面板
   或探针里现算 —— 现算的数无法与日志对上。
2. 计数器**只增不减**，复位由 `_delta` 夹住；不要在层里手动清零。
3. 加了上报字段就必须同时加进 `latency_monitor.STREAM_METRIC_KEYS` **和**
   `video.CLIENT_TIMING_KEYS`（有测试断言两者集合相等），计数型还要进
   `CLIENT_TIMING_COUNT_KEYS`，否则 `/video/timing` 里会出现 `1234.0`。
4. 面板显示新口径前，先确认它**能区分**已有的两种结论；不能区分就放进明细格，
   不要抢主数字。
